## Remote Call AI 기능 설계 및 스쿼드 리딩

### Spring Modulith로 경계만 강제

* 처음 구축할 때부터 도메인 분리 전략을 세웠고, 이후 MSA 분리를 고려한 설계였음
* 운영 배포 전 검토에서 현재 규모 대비 배포·운영 비용이 크다고 판단
* 레퍼런스를 찾다가 모듈러 모놀리스를 택함 — 서버는 나누지 않고 Spring Modulith로 모듈 경계만 강제

### 모듈 간 연계

* 모듈 간 연계는 Spring 이벤트로 분리
* 꼭 필요한 흐름만 같은 트랜잭션으로 묶고, 대부분은 분리

### 이벤트 소싱

* 상태와 통계의 정확성이 요구됨
* 초기에는 경우의 수를 예상할 수 있지만, 피어나 디바이스가 늘어나는 확장을 고려하면 이벤트가 통계의 근거가 되고 언제든 신뢰할 수 있는 상태를 복원할 수 있음
* 관제용 조회는 CQRS 읽기 모델로 투영

### 응답 판단을 파이프라인 노드로 분리

* 응답시간과 품질을 개선하려면 문제 지점을 도출해야 하는데, 단일 노드로는 판단이 어려움
* RAG 정보가 중요한 프로젝트라 RAG 도구 사용 여부, RAG 응답 수준, RAG 응답에 따른 결과물 차이를 측정해야 했음
* 그래서 분류·검색·LLM-as-a-Judge를 노드로 분리

### AI 응답 판정

* 정형 응답은 명세와 대조
* 비정형 응답에는 규칙을 둘 수 없어 골든셋과 트레이싱으로 판정
* 골든셋은 도메인에 특화된 상담 이력으로 만듦
* 트레이싱과 모니터링은 Langfuse
* 판정 노드의 판단은 사람이 피드백과 벤치마크로 보정

## Remote View SaaS 구조 개선

### 비정규화 대신 메모리 재귀 탐색

* 비정규화된 데이터는 이해를 요구하는 코드를 만들고 확장성이 떨어진다고 판단
* 정규화 구조를 유지한 채 회사 단위 계층을 DB 조회 1회로 가져와 메모리에서 재귀 탐색

### 회사 단위 통합 캐시

* 캐시에는 식별자만 올림 — 회사 단위로 묶어도 메모리 부담이 문제 될 양이 아니었음

## 다임즈·파이오링크 NMS·EMS 시기

주업무가 NMS였던 시기입니다.

* 다임즈 EMS는 서버·DB·WAS 등을 감시했고, 고객은 공공기관이 가장 많았음
* SNMP와 웹소켓을 다룸 — 트랩과 syslog는 시스템에 있었지만 직접 다루지는 않음
* 파이오링크는 장비 회사라 장비 쪽 에이전트와 웹으로 통신해 상태를 수집하고 관제 — 에이전트 개발은 직접 하지 않음
* 임계치·이벤트 구성과 알람을 개발
* 다른 시스템과의 연동은 상시 업무
* 현장에 나가 고객과 직접 소통 — 미팅, 니즈 도출, 설계, 배포, 운영까지 수행
* 수집 데이터 정합성 문제도 다뤘지만 정리하기 애매해 이력서에는 쓰지 않음
